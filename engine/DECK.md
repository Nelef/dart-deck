# 덱 엔진 사용법 · 작성 규칙

발표 덱이 함께 쓰는 엔진과, 덱을 만들 때 지키는 규칙이다.
규칙은 사용자가 덱을 여러 번 고쳐 주며 정한 것이다(2026-09-28 ~ 29).


> **DART Deck 에서 읽을 때**(2026-09-30): 이 문서는 이전 프로토타입에서 옮겨 왔다. 아래 1장의 `serve.py` ·
> localhost/Tailscale 제한 이야기는 여기서는 `server/app.py` · 계정별 덱 폴더(`data/decks/<계정>/<덱>/`) · 로그인한 주인 · 관리자로 읽는다.
> 덱 폴더의 `js/` `css/` `tools/` `DECK.md` 는 엔진(`engine/`)을 가리키는 링크다 — 고치지 않는다. 고칠 것은 덱 `index.html` 하나다.

## 1. 엔진 — 새 덱은 장 마크업 + `Deck.create` 한 번

| 파일 | 맡는 것 |
|---|---|
| `css/deck.css` | 공용 스타일 · 색 변수(`--vl` `--pps` `--aio` `--llm` `--code` `--ok` `--bad` …) · **글자 크기 변수(`--fs-*`, 아래 3)** |
| `js/deck.js` | 16:9 무대 맞춤 · 장/단계 · 목차 · 조작줄 · 자동 재생 · 자막 모드 · 주소(`#n`) |
| `js/deckviz.js` | 문서 그림(원본 픽셀 좌표 SVG) · 카메라 이동 · 상자 · 숫자 올리기 · **입체 그래프**(`bar3d` · `stack3d` · `ring3d`) · **순서도**(`fcNode` · `fcArrow`) |
| `js/deckkit.js` | 옆 패널 — 코드 경로 · AI 에게 묻기 · 세부 카드 (선택) |
| `js/deckzoom.js` | 확대·축소 (선택) |

**AI 에게 묻기는 모든 덱에 붙인다**(사용자 지적 2026-09-29 — "엔진에 AI 기능 있지 않나, 왜 안 보이지").
`<script src="js/deckkit.js">` 를 넣고 `Deck.create({ onReady: () => DeckKit.init({...}) })` 로 연다.
넘길 것: `current` · `goto` · `stageOf`(코드 단계, 없으면 `() => null`) · `contextOf`(그 장 숫자의 원자료 — AI 가 근거로 삼는다) ·
`suggest`(장마다 추천 질문) · `intro`(덱 소개 + 답하는 방식). 일반 사용자용처럼 코드를 보일 일이 없으면 `noCode: true`, `codemap: null`.
`wholeDeck: true` 면 질문마다 **덱 전체**(모든 장의 번호 · 화면 글 · 원자료)와 지금 장을 보내고, AI 가 여러 장에서 근거를 모아
`[장 이름](#번호)` 링크를 단다 — 패널에서 누르면 그 장으로 간다. 화면의 굵은 글씨·색처럼 **글로 안 넘어가는 뜻**은 AI 가 못 본다:
핵심 사실은 `intro` 에 글로 박는다(실측 — 굵은 글씨로만 표시한 핵심 사실을 AI 가 놓치고 다른 항목으로 답했다).
`editable: true` 면 **간단한 수정도 맡긴다**(2026-09-29): "~ 바꿔줘/고쳐줘/빼줘" 같은 질문이면 덱 원본(지금 장 마크업 · 그 장 스크립트 · 전체)을 싣고,
AI 가 `<<<<<<< 찾기 / ======= / >>>>>>> 바꾸기` 블록을 낸다(JSON 은 이스케이프를 틀려 버렸다). 패널이 찾을 글이 **정확히 한 번**인지 세어 보여 주고,
[적용]을 누르면 `serve.py` 의 `/api/edit` 가 다시 세고 `.deck-edits/` 에 백업한 뒤 저장한다 — 새로고침 뒤에도 대화가 이어지고 [되돌리기]가 있다.
localhost 와 **Tailscale 기기(100.64.0.0/10 — 폰 등 같은 계정 tailnet)**에서만 된다(같은 와이파이의 남은 막힘). http 주소라 브라우저 암호 API 가 없을 때는 `deckcheck.js` 의 순수 JS SHA-256 을 쓴다. **커밋은 사람이 한다.**
**레이아웃을 크게 바꾸는 건 지금 장만**(사용자 지정 2026-09-29): AI 가 지금 장의 `<section>` 과 `INIT['장 이름']` 을 새로 써서 ```html · ```js 코드 칸에 낸다
(gemma 는 약속한 블록에 원본을 넣고 완성본을 코드 칸에 넣는 버릇이 있어 코드 칸을 1차로 받는다). 찾을 글은 AI 에게 받지 않고 패널이 원본에서 자른 그 장이다 —
서버도 같은 규칙으로 잘라 한 글자라도 다르면 거부한다. 원본과 똑같은 답 · 장 이름이 바뀐 답 · 마크업 안 `<script>` 는 거부. 작은 수정의 찾기는 600자 상한.
적용 뒤 새로고침에서 스크립트 오류 · 무대 밖 넘침을 점검해 수정안 밑에 적는다(있으면 [되돌리기] 권함). 다른 장 · 공용 `<style>` · 데이터 · 새 장은 Claude Code 로.
**자가검증**(2026-09-29): 수정안은 곧바로 [적용]이 아니다 — 원본 옆 숨김 사본(`.deckpreview-*.html`)에 적용해 그 장을 캡처하고 모든 장을 점검한 뒤(`serve.py /api/shot` → `tools/deck_shot.cjs`),
그림과 '원래 없던 문제' 목록을 AI 에게 보여 스스로 검증하게 한다. "검증 통과"이면서 자동 점검도 0 일 때만 [적용], 아니면 AI 가 고친 안으로 다시 — **최대 3번, 안 되면 롤백**(원본은 안 바뀜).
글 피드백만 줬을 땐 문제가 142→154→172 로 늘었고, 그림을 주자 74→0 으로 수렴했다. 한계: '요청대로 됐나'는 AI 판정이라 너그럽다.

**✎ 편집(사람이 직접, PPT 식 — `js/deckedit.js` 핵심 + `js/deckedit-ribbon.js` 리본)** — 조작줄 ✎ 편집 또는 E 키(2026-09-29 확장).
- 고르기: 누르면 장 바로 아래 덩어리 · 또 누르면 그 안쪽 · Alt(⌥) = 가장 안쪽 · Shift = 여럿 · ⌘/Ctrl+A = 전부. 끌기(맞춤선: 무대 가장자리 · 가운데 · 여백 72 · 다른 덩어리에 붙음, Alt 로 끔),
  모서리 8개 = 크기, 위 동그라미 = 돌리기(15°씩, Shift 자유), 방향키 1px(Shift 10px), 숫자 칸 X · Y · W · H · 회전.
- 글: 두 번 누르기(폰은 두 번 탭) · Enter 로 고치기. 리본의 글꼴 · 크기(pt) · 굵게 · 기울임 · 밑줄 · 취소선 · 글자색 · 형광 · 정렬 · 줄 간격 · 자간은
  **고치는 중이면 고른 글자에만**, 아니면 고른 요소 전체에. 글꼴은 전부 Google Fonts 웹 글꼴 15종 — 저장할 때 쓴 글꼴을 덱 머리 글꼴 줄에 더해 Windows · Mac 이 같게.
- 도형: 채우기 · 테두리(색 · 두께 · 모양 — 개별 속성으로만) · 둥글기 · 그림자 · 투명도 · 여백. 넣기: 글상자 · 사각형 · 둥근 · 원 · 선 · 화살표 · 그림(serve.py /api/asset → img/uploads/).
- 복제(⌘/Ctrl+D) · 지우기(Delete) · 복사/붙이기 · 앞뒤 순서 · 맞춤 6가지(하나면 무대, 여럿이면 서로) · 간격 같게(셋 이상) · 되돌리기/다시(⌘/Ctrl+Z · Shift+Z/Y) · 저장(⌘/Ctrl+S).
- **AI 가 고친 것도 편집 — 고정**: 스크립트(INIT)가 그린 요소(주황 점선)를 사람이 고치면 **묻지 않고** 그 장을 '지금 화면 그대로 고정'한다(장에 `data-frozen="날짜"`,
  deck.js 가 그 장의 INIT 을 건너뛴다 — 스크립트는 파일에 남아 표시를 지우면 다시 그린다). 고정하지 않으면 다음에 열 때 스크립트가 다시 그려 편집이 덮인다.
  한계: 고정된 장은 데이터가 바뀌어도 다시 그려지지 않는다. 예전 방식(INIT 을 `/* 굳힘 */` 으로 비움)도 고정된 장으로 본다. 목록으로 만든 스크립트(간지)는
  '화면 글 ≠ 파일 글'로 알아본다(2026-09-30). 화면 말은 '고정'(예전 '굳히기'는 한국에서 안 쓰는 말이라 바꿈).
- **단계(리본 [단계] 탭, js/deckedit-steps.js — 2026-09-30)**: 한 페이지 안에서 차례로 나타나기(PPT 애니메이션). 미리보기 ◀ 처음 · 1단계 … ▶(자막 · 훅까지 그 단계로),
  고른 것 [항상] · [이 단계부터](`data-at`) · [이 단계에만](`data-only`), 페이지 단계 수 ＋/−(`data-steps`), 요소마다 번호 딱지(「2~」 · 「1·2」). 다른 단계 것은 흐리게 · 못 누름 —
  그 단계로 옮겨서 고친다. 자막(`captions`)은 스크립트 안 글이라 여기서 못 고친다(AI 에게 부탁).
- **장 목록(왼쪽 썸네일, js/deckedit-slides.js)**: 편집을 켜면 조작줄이 내려가고 왼쪽에 모든 장이 뜬다. 누르면 그 장으로(저장 안 한 편집이 있으면 막음),
  우클릭 = 다음에 새 장 추가 · 이 장 복제 · 장 복사 · 다음에 붙여넣기, 목록을 누른 뒤 Ctrl/⌘+D · C · V. 새 장 · 복제본은 고정된 장으로 들어가고
  저장 뒤 새로고침해 새 장에서 편집을 이어 연다. 좁은 화면(폭 ≤640 · 높이 ≤500)에는 목록을 띄우지 않는다.
- Windows = Mac: 글꼴 웹 글꼴만(deck.css 에 Noto Sans Symbols 2 대체 — Noto Sans KR 에 없는 ✓ ✎ ✦ ✕ ⛶ ↻ 가 OS 글꼴로 넘어갔다), 이모지 안 씀, 단축키 Ctrl · ⌘ 둘 다, 포인터 이벤트(마우스 · 터치 같음).

## 2. 말 — 단어부터 고르고, 제목은 명사형, 설명은 개조식

**단어는 먼저 고르게 한다.** 새 덱은 쓸 말의 후보를 표로 보여 사용자가 고른 뒤 초안을 쓴다(일반 한국인이 쓰는 말).
고른 말은 덱 머리에 적어 두고 덱 전체에서 같은 말만 쓴다(예: 매출 · 영업이익 · 전년 대비 · 부문 · 페이지). 처음 보는 말은 괄호로 한 번 풀어 준다.
만든 말 금지("견디기"·"한목소리"·"되풀이 상한") — 일반 사용자가 쓰는 말로 바꾼다.

**문서의 한 장은 '페이지'로 쓴다 — '쪽'은 쓰지 않는다**(사용자 지정 2026-10-06). `3쪽` → `3페이지`, `쪽마다` → `페이지마다`,
`쪽당` → `페이지당`, `여러 쪽` → `여러 페이지`. 조사도 함께 바꾼다(`쪽이` → `페이지가`, `쪽은` → `페이지는`, `쪽을` → `페이지를`).
방향을 뜻하는 말(왼쪽 · 오른쪽 · 좋은 쪽 · 어느 쪽)은 그대로 둔다. 글이 길어져 상자를 넘치면 글자를 줄이지 말고 말을 줄인다(3장).

**제목은 명사형**(단어 나열). 문장형 제목은 우리 발표 문화에 맞지 않는다(사용자 지적).

| ✗ | ✓ |
|---|---|
| 영업이익이 크게 늘었습니다 | 영업이익 — 3개년 추이 |
| 부문마다 매출 구조가 다릅니다 | 부문별 매출 구성 |

**설명은 개조식** — 국내 발표 자료의 관례다.
- 명사형으로 끝낸다(`~함` · `~음` · 명사). `~합니다` 체를 쓰지 않는다. 한 덱 안에서 서술식과 섞지 않는다.
- 한 줄에 사실 하나. 2~3줄이면 충분하다.
- **이유를 먼저** 쓴다 — 이유 줄 다음에 `→` 대응 줄(`ul.pts` 의 `li` 와 `li.to`).
  ```
  ▪ 수작업 집계라 월말마다 숫자가 어긋남
    → 원천 데이터에서 자동 집계, 어긋난 항목만 사람이 확인
  ```
- 예외: 영상처럼 틀어 두는 자막 덱의 자막은 합니다체 — 말로 읽히는 글이라서다.

**제목 밑 설명 두 줄(`ul.pts`)은 꼭 필요할 때만 넣는다**(보는 사람은 제목 밑 설명 줄을 잘 읽지 않는다).
- 기본은 **제목 + 그림**이다. 그림(인포그래픽 · 숫자)이 말하게 하고, 제목 밑 글머리표는 두지 않는다.
- 넣는 경우는 하나 — 그림만으로는 **결론을 잘못 읽을** 위험이 있을 때(예: 합계는 늘었는데 일부 부문은 줄었음). 그때도 한 줄.
- 빼면 본문을 제목 바로 아래(무대 y ≈ 178)부터 시작한다 — 글머리표 자리를 비워 두지 않는다.
- 설명이 더 필요하면 글을 늘리지 말고 **단계 · 요소마다 한 장을 따로** 만든다(아래).

**단계마다 한 장 — 인포그래픽 + 결과 + 셈**.
- 여러 단계를 한 장에 모은 장(예: 수집 · 정리 · 검토) 뒤에 **단계 하나당 한 장**을 둔다. 앞 장의 카드를 누르면 그 장으로 간다.
- 짜임: 위 = 그 단계가 한 일의 인포그래픽(실제 실행 기록의 값) · 아래 왼쪽 = 결과(퍼센트 크게 · 모수 작게) · 아래 오른쪽 = 그 단계와 엮인 셈(셈이 다른 항목은 따로, 예시 하나로 실제 계산).
- 표 형태로 단계를 줄줄이 푼 '설명 장'(`설명 — 앞 장 제목`)은 만들지 않는다 — 2026-10-13 "4 · 6 · 7"(단계 번호 ④⑥⑦)을 페이지 번호로 잘못 읽고 만들었다가 둘 다 뺐다.

**지표마다 "무엇을 센 숫자인지" 한 문장**(사용자 2026-10-13 — "설명 없이 ppt 만 봐도 이해될 수 있게").
- 지표 이름은 무엇의 비율인지 드러나게(`맞음` ✗ → `자동 처리 정답률` · `확정 비율`), 한 줄로(두 줄로 접으면 줄마다 높이를 버린다).
- 퍼센트 바로 아래 작은 글 한 문장에 **분모와 분자를 말로**: `응답 520건 중 515건이 정답` · `값을 바꾼 41건 중 39건 바르게 고침 / 2건은 잘못 바꿈`. 두 줄이면 뜻 단위로 `<br>` — 자동 줄바꿈에 맡기면 `336건만 ·` 처럼 어색하게 끊긴다.
- 숫자의 기준(대상 몇 종 · 문서 몇 건 · 회차 · 공식 집계인지)은 각주 맨 앞에.
- 넘침은 눈대중 말고 잰다: 글자 줄이 카드 안쪽 여백을 넘는지 + 카드가 놓인 칸 아래로 벗어나는지 둘 다(카드 안만 보면 카드가 통째로 길어진 걸 놓친다). `white-space:nowrap` 설명 줄은 카드 밖으로 새므로 쓰지 않는다.

**목차 + 간지** — 처음 보는 사람이 장마다 맥락을 잃지 않게(사용자 지적 2026-09-29).
- 첫 장은 목차: 부분마다 번호 · 부분 이름(한 단어) · 부분이 답할 물음 · 들어 있는 장 이름.
- 부분이 시작할 때마다 간지 한 장: 큰 번호 · 부분 이름 · 물음, 오른쪽에 목차 진행 표시. "앞에서 · 이번에" 문맥 줄은 넣지 않는다(사용자 지시 2026-09-29).
- 조작줄 이름이 겹치지 않게 간지는 `1 결과`, 내용 장은 `정답률`처럼 다른 이름을 쓴다. (`PARTS` 설정).

## 3. 글자 크기 — `css/deck.css` 의 `--fs-*`

무대 1600px 는 PPT 16:9 한 장(13.33in)과 같아 **1pt = 1.667px** 다.
기준: 제목 36~44pt · 본문 18~24pt(띄워 발표하면 20pt 이상) · 국내 발표 자료 본문 최소 14~18pt.

| 변수 | px | pt | 쓰는 곳 |
|---|---:|---:|---|
| `--fs-title` | 60 | 36 | 장 제목 |
| `--fs-body` | 34 | 20 | 설명 글머리표 |
| `--fs-box` | 28 | 17 | 상자·카드 제목, 표의 첫 열 |
| `--fs-small` | 24 | 14 | 상자 안 설명 · 표 · 범례 — **이보다 작게 쓰지 않는다** |
| `--fs-foot` | 20 | 12 | 각주·출처만(읽지 않아도 되는 글) |

- 글자가 크면 들어갈 말이 준다 — **말을 줄이고 그림으로 보인다**(아래 4). 넘치면 글자를 줄이지 말고 말을 줄인다.
- 옛 덱은 아직 이 변수를 쓰지 않을 수 있다(옮기면 화면이 바뀐다). 새 덱부터 쓴다.
- 확인은 재서 한다 — 모든 장의 글자 크기를 px·pt 로 뽑아 14pt 미만(각주 제외)이 없는지 본다.

## 4. 인포그래픽 — 숫자는 그림으로, 한 장에 메시지 하나

- **이모지는 쓰지 않는다**(사용자 지정 2026-10-01) — 📜 ✅ 🚀 ⚠️ 1️⃣ 같은 그림 글자는 덱 글꼴에 없어 컴퓨터(맥 · 윈도 · 서버)마다 다른 그림으로 그려지고 PDF 도 달라진다.
  아이콘은 SVG 로 그리거나 덱 글꼴에 있는 기호 글자(✓ · ● · ▶ · ★ · → · ①)를 쓴다. 화면 점검(js/deckcheck.js)이 이모지를 문제로 잡는다.

- 비율은 **100칸 격자**(한 칸 = 1%) 나 막대, 몫은 도넛, 나눔은 한 줄 누적 막대, 과정은 **상자 + 화살표** 두 줄 비교.
- 예시는 **실제 문서 그림**(원본 페이지 · LLM 에 보낸 부분 그림)과 실제 입출력으로. 꾸민 그림을 쓰지 않는다.
- 그림 옆에는 그 그림이 말하는 숫자 하나만 크게 둔다.
- **숫자는 오른쪽 정렬**(사용자 지정 2026-10-06) — 세로로 줄지어 나오는 숫자(표의 숫자 열 · 막대 옆 값 · 시간 · 인식률 · GB · 개수처럼
  단위가 같은 값)는 칸 폭을 정해 오른쪽 끝을 맞추고, 자릿수 폭이 같은 숫자(`font-variant-numeric: tabular-nums`)를 쓴다.
  「12.3 → 45.6%」처럼 두 값을 잇는 칸도 오른쪽 끝을 맞춘다. 막대 끝에 붙어 위치가 곧 값인 글(타임라인 끝 시간 등)은 예외.
- **값 · 데이터 글자는 칩이나 바탕 안에 넣는다**(사용자 지정 2026-10-07) — 읽어 온 글자 · LLM 답 · 데이터 한 줄 · 「이름 값」 짝 ·
  코드 값처럼 **데이터를 보이는 글**은 맨글자로 늘어놓지 않는다. 고정폭 글자를 띄어쓰기로만 나누면 어디까지가 한 값인지 안 보인다
  (값 두 개를 띄어쓰기로만 늘어놓으면 "글자 간 경계가 없어 가독성이 떨어진다").
  - 값 하나 = 둥근 네모 칩 하나(`--c-neutral-tint` 바탕). 이름(출처 · 항목 이름)은 칩 **앞의 작은 회색 굵은 글**로, 칩 안에 넣지 않는다.
  - 뜻이 있으면 칩 색으로 — 맞음 · 최종 값 = 파랑 칩(`--c-brand-tint`), 틀림 · 다름 = 빨강 칩(`--c-alert-tint`). 빨강 한두 곳 규칙(6)은 그대로.
  - 표 한 줄(데이터 행)은 **칸마다 칩**으로 나눈다 — `|` 구분 글자를 그대로 보이지 않는다. 머리 줄은 굵은 칩.
  - 설명 문장(개조식 글머리표 · 각주)은 칩으로 만들지 않는다 — 칩은 값에만.
- **수치 그래프는 입체(3D)로 그린다**(사용자 지정 2026-09-29) — 엔진 부품 `Viz.bar3d`(막대) · `Viz.stack3d`(누적 막대) ·
  `Viz.ring3d`(도넛) 을 쓰고, 칸 격자는 `.grid100` 처럼 옆면 그림자를 붙인다.
  단, **원근은 쓰지 않는다** — 앞면 길이·각도가 값 그대로이고 윗면·옆면만 덧붙인다(원근·기울임은 크기를 부풀려 값을 속인다).
  면의 밝기는 같은 색을 흰색·검정과 섞어 만든다(`Viz.shade`) — 새 색을 만들지 않는다.
  누운 도넛은 구멍이 납작해 가운데 숫자가 가린다 — 숫자는 도넛 아래에 크게 둔다.
  **예외 — 막대가 많은 비교(예: 17개 × 2 = 34개)는 평면으로** 그린다. 윗면·옆면이 서로 겹쳐 오히려 읽기 어렵다(사용자 지적 2026-09-29 "3d 니까 더 별로").
- **항목이 많은 비교(예: 항목 17개의 전 · 후)는 표 + 차이 막대로** 보인다(사용자 선택 2026-09-29 — 세로·입체·가로 막대를 거쳐 정함).
  열은 이름 · 개수 · 비교 대상 % · 좋은 쪽 % · 차이 %p, **차이 열에만** 짧은 막대(오름 파랑 · 내림 빨강). 항목은 전부(앞 몇 개 + "나머지"로 묶지 않는다).
  %p 로 정렬하면 개수가 적은 항목이 위로 온다(3필드 중 1개 = +33.3%p) — **개수 열을 꼭 둔다.**
  강조할 묶음은 굵은 글씨로 하고 뜻은 각주에 적는다. 파란 배경 띠는 쓰지 않는다. 막대 그래프로 그릴 때는 두 값 막대를 겹치지 말고 따로 놓는다.
- **과정은 순서도로 그린다**(사용자 지정 2026-09-29) — `Viz.fcNode(kind, …)` · `Viz.fcArrow(pts, …)`.
  표준 기호: 시작·끝 = 둥근 끝 상자(`term`) · 처리 = 사각형(`proc`) · 판단 = 마름모(`dec`) · 입출력 = 평행사변형(`io`), 위에서 아래로 화살표.
  실제로 갈라지는 곳(예: "자료 종류" → 표 / 글)만 마름모로 그린다 — 결과를 판단처럼 그리지 않는다.
  갈래 이름은 선 위에 둔다(마름모 끝에 붙이면 겹친다). 비교는 두 줄을 나란히(전 회색 · 후 파랑).

## 5. 숫자 — 기록에서 계산하고, 출처를 적는다

- 화면의 숫자는 **재료 JSON 에서 계산**한다. 재료는 DB·실행 기록에서 뽑는 스크립트로 만든다(`data/*_build.py`) — 손으로 적지 않는다.
- 비교하는 두 숫자는 **같은 장비·같은 모델·같은 시기**의 회차로 짝짓는다. 섞으면 그렇다고 적는다.
- 합이 맞는지 본다(예: 전체 217건 = 그대로 199 + 수정 9 + 확인 필요 9). 나눔은 코드의 분류 그대로 쓴다.
- 측정일·출처·단서(같은 기준이 아닌 비교 등)는 각주(`--fs-foot`)로 남긴다.
- **비율은 퍼센트가 주인공, 개수는 그 밑에 작게**(사용자 지정 2026-10-12) — 「전체 5,411개 중 3,497개(64.6%)」처럼 모수가 있는 값은
  큰 숫자를 **%** 로 쓰고, 바로 아랫줄에 작은 글씨(`.sm`)로 **개수**(`3,497개`)를 적는다. 모수는 이름 아래 회색 글로(「전체 5,411개 중」).
  v1 → v2 처럼 두 값을 잇는 칸도 같다(양쪽 다 % 크게 · 개수 작게). 개수가 큰 숫자가 되면 모수가 다른 비교에서 크기가 거꾸로 읽힌다.
  모수가 없는 값(글자 수 · 초 · GB)은 이 규칙 밖 — 그 값 자체를 크게 쓴다.

## 6. 색 — 청록 한 가족 + 회색 + 빨강 하나

색이 많으면 강조가 사라진다. 그래서 **색 가족을 셋으로 묶는다**(사용자 지정 2026-09-29: "파란색 계열 · 너무 많은 색 금지").
기준은 **60-30-10** — 바탕(흰색·연회색) 60 · 글자와 회색 요소 30 · 파랑 강조 10. 강조색은 아껴 써야 힘이 있다.

| 변수 | 값 | 흰 바탕 대비 | 쓰는 곳 |
|---|---|---:|---|
| `--c-brand` | `#0F766E` | 4.62 | 강조 파랑 — v2 · 좋은 쪽 · 핵심 숫자 · 글머리 기호. 브랜드 대표색(2026-09-29 확인) |
| `--c-brand-deep` | `#134E4A` | 10.4 | 진한 남색 — 이름표(엔진 이름 · 알고리즘) · 굵은 글자 |
| `--c-brand-mid` | `#9DB2F7` | 2.1 | 중간 파랑 — **면 채우기만**(막대의 둘째 조각) |
| `--c-brand-tint` | `#E8EEFD` | — | 옅은 파랑 — 좋은 쪽 결과 상자 바탕 |
| `--c-neutral` · `--c-neutral-tint` | `#8D95A1` · `#E9EBEE` | — | 회색 — v1 · 비교 대상 · 막대 바닥 |
| `--c-alert` · `--c-alert-tint` | `#DC2626` · `#FEE2E2` | 4.83 | 빨강 — **틀림 · 누락 · 문제에만** |
| `--c-text-mute` | `#6B7280` | 4.8 | 흐린 글자(각주 · 보조 설명) |

- **비교는 "v1 = 회색 · v2 = 파랑"** 으로 고정한다. 좋은 쪽을 초록으로 칠하지 않는다(파랑이 좋은 쪽이다).
- **엔진은 색으로 구분하지 않는다** — 이름표는 모두 남색(`--c-brand-deep`)이고 글자로 구분한다. 옛 덱의 엔진별 색
  (`--vl` 주황 · `--pps` 보라 · `--aio` 하늘 · `--llm` 자홍 · `--code`)과 `--ok` 초록은 새 덱에서 쓰지 않는다.
  - 예외(사용자 지정 2026-10-08): **두 엔진 비교가 주제인 덱**에서 "어느 쪽이 나았는지 색으로" 를 요청받으면 파랑 농도로만 가른다 —
    엔진 A = 진한 색(`--c-brand-deep`) · 엔진 B = 강조색(`--c-brand`) · 같음/문서별 = 회색. 정했으면 **덱 전체**(막대 · 점 · 칩 · 범례)에서 같은 엔진은 같은 색이다
    (한 장의 점 그래프는 남색인데 막대는 파랑이던 실수). 두 계열 이상은 색만으로 가르지 않는다 — 점 모양(● ■)과 이름표를 함께 단다.
- 나눔 막대처럼 한 그림에 여러 칸이 필요하면 **파랑 농도**(`--c-brand` → `--c-brand-mid` → `--c-brand-deep`)로 가른다. 새 색을 만들지 않는다.
- 글자는 흰 바탕 대비 **4.5:1 이상**(WCAG AA)인 색만 쓴다 — `--mute`(#9aa1ab, 2.6)와 `--c-brand-mid` 는 글자에 쓰지 않는다.
- 한 장에서 빨강은 문제를 짚는 한두 곳에만 쓴다.

## 7. 정렬 · 간격 — 자동 점검이 못 보는 것

사용자 지적(2026-10-08, 엔진 비교 덱): "ui 가 이쁘게 정렬 안 되어 있다 · 텍스트끼리 너무 딱 붙는다".
자동 점검(넘침 · 겹침)은 통과했는데 화면은 어수선했다 — 아래는 그때 고친 것이다.

- **본문 시작선을 하나로** — 제목 아래 첫 요소는 무대 y = 185 에서 시작한다(제목과 약 35px). 머리 칩 · 카드가 제목에 붙지 않게.
- **나란한 열은 위 · 아래 끝선을 맞춘다** — 왼쪽 · 오른쪽을 모두 카드로 만들고 같은 위(예 225) · 아래(예 692)에서 끝낸다.
  남는 높이는 마지막 카드가 채운다(`flex: 1`). 한쪽만 짧게 끝나거나, 아래 띠(사실 · 결론 띠)에 잘리면 안 된다.
- **간격은 한 값으로** — 카드 사이 14px, 글 묶음 사이 6px 이상(목록 항목 `li + li` 6px · 표 머리 아래 8px · 범례와 설명 사이).
  재서 확인한다: 글을 가진 요소끼리 위아래 · 좌우 간격 6px 미만인 쌍을 센다(머리말 ↔ 제목은 엔진 공용 배치라 뺀다).
- **이름 ─ 값 줄은 이름 칸 폭을 같게** — 같은 카드 안에서 가장 긴 이름(예 「최종 26B」)에 맞춰, 값 칩의 왼쪽 끝이 한 줄로 선다.
- **잘라 온 문서 그림은 칸 폭을 채운다**(`object-fit: cover`) — 넓은 틀 안에 작은 그림이 한쪽에 붙거나 회색 여백 띠가 생기면 안 된다.
- **덱 클래스 이름이 엔진 css 와 겹치지 않게** — 엔진의 `.card` 는 `position: absolute` 라, 덱에서 같은 이름을 쓰면 카드가 한 자리에 쌓인다.
  새 클래스를 만들기 전에 `css/deck.css` 에 같은 이름이 있는지 본다.
- **표의 차이 칸은 좋아진 쪽만 파랑** — 나빠진 쪽을 모두 빨강으로 칠하면 한 장에 빨강이 서너 곳이 된다(6 의 한두 곳 규칙). 빨강은 짚을 칸에만.

## 8. 끝내기 전 확인

- 모든 장·단계를 브라우저로 열어 **콘솔 오류 0 · 무대 밖 넘침 0 · 겹침 0** 을 본다(스크린샷).
- 글자 크기를 재서 기준(3)을 지키는지 본다.
- 밝은 테마만 — 흰 바탕에 흰 글자 같은 다크 테마 잔재가 없게 한다.
- 색은 6의 변수만 쓰였는지 본다(덱 파일에 `#rrggbb` 직접 적은 색이 없어야 한다).
- 데이터 글자 · 값 · 표 줄이 맨글자로 나열된 곳이 없는지 본다 — 값마다 칩(4).
- **모든 장을 그림으로 찍어 눈으로 본다**(7) — 끝선 · 간격 · 잘림 · 빈 틀 · 같은 엔진 같은 색. 넘침 · 겹침 0 은 정렬이 맞다는 뜻이 아니다.
- 한 장의 빨강이 두 곳 이하인지 센다(6).
